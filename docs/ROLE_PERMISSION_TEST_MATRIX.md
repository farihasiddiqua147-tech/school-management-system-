# Role-based API security test matrix

This matrix defines the minimum acceptance tests before a school stores real student records. A checked box means a test has actually passed in an automated run; merely documenting it does not count.

## Test setup

Use a disposable database populated with synthetic accounts for admin, teacher, student A, student B, guardian A linked only to student A, guardian B linked only to student B, and accountant. Never use real student data in test fixtures. Keep credentials and tokens generated by the test process; do not commit them.

## Required assertions

| Area | Anonymous | Admin | Teacher | Student | Guardian | Accountant |
|---|---|---|---|---|---|---|
| Health endpoint | Public health only | Same | Same | Same | Same | Same |
| Login | Valid login works; invalid credentials return generic 401 | Same | Same | Same | Same | Same |
| User administration | 401 | Can create users; cannot read password hashes | 403 | 403 | 403 | 403 |
| School settings | 401 | Read/write | Read-only if policy permits | Read-only if policy permits | Read-only if policy permits | Read-only if policy permits |
| Student directory | 401 | Authorized school scope | Only permitted school/class scope | Own record only | Linked children only | Only fields required for billing |
| Attendance | 401 | Authorized management | Mark/read permitted classes only | Own attendance only | Linked children only | 403 unless explicitly needed |
| Exams and results | 401 | Authorized management | Permitted classes only | Own results only | Linked children only | 403 unless explicitly needed |
| Fees and payment receipts | 401 | Authorized management | 403 unless explicitly needed | Own fee summary only | Linked children only | Create/read billing records |
| Expenses and accounting reports | 401 | Read/write | 403 | 403 | 403 | Read/write as accounting policy allows |
| Notices | 401 | Publish/manage | Only authorized publishing actions | Published notices for intended audience | Published notices for intended audience | Read-only unless authorized |
| Guardian linking | 401 | Authorized linking | No arbitrary relinking | Cannot change guardian links | Cannot add another family's child | Cannot change guardian links |
| Audit logs | 401 | Read access with sensitive fields minimized | No unrestricted access | 403 | 403 | No unrestricted access |

## Cross-record isolation tests

- [ ] Student A cannot retrieve Student B's profile, attendance, results, fee data, or receipt by changing an ID in the URL or request body.
- [ ] Guardian A cannot retrieve Student B's information, even if the request supplies Student B's ID.
- [ ] A guardian whose account is inactive or whose child link is inactive cannot use stale links.
- [ ] Teacher class restrictions are checked on the server, not only hidden in the interface.
- [ ] Accountant permissions do not imply access to authentication secrets or unrestricted student academic records.
- [ ] Changing the role claim in a forged JWT fails signature verification; a valid token for a deactivated user is rejected.
- [ ] Unauthenticated and wrong-role requests do not mutate data.
- [ ] Duplicate attendance and result submissions return a controlled conflict/validation response and do not create duplicate records.
- [ ] Invalid IDs, oversized fields, malformed JSON, invalid dates, negative amounts, and unknown enum values are rejected safely.
- [ ] Errors do not disclose SQL statements, filesystem paths, tokens, password hashes, payment credentials, or database URLs.

## Data-integrity tests

- [ ] Fee payments cannot exceed the outstanding balance unless an explicit approved policy permits it.
- [ ] Receipt numbers are unique and payment plus fee-balance updates are atomic.
- [ ] Expense creation and audit logging succeed or fail together.
- [ ] GPA/grade calculations cover zero, boundary marks, missing subjects, and failing marks according to the school's documented grading policy.
- [ ] Report totals reconcile with ledger entries; legacy balances without ledger entries are reported separately.
- [ ] Deleting/deactivating a user does not silently orphan required student/guardian ownership relationships.

## Release evidence

For each run, record commit SHA, database engine/version, test command, pass/fail counts, and unresolved failures. Keep evidence free of personal student data and secrets. A passing syntax check or unit-test suite is not a substitute for these integration tests.

## Current status

**Not yet demonstrated complete.** This is an acceptance matrix. It does not claim that all endpoints have been tested, and it does not replace implementation of the PostgreSQL runtime adapter or a real migration/restore rehearsal.
